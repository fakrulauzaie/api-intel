# Contributing

Thank you for helping improve evidence-backed static analysis for legacy NestJS
systems. The repository is still preparing its first public alpha. Issue and pull-
request intake must remain disabled until the private security and conduct-reporting
channels listed in the release gates are active.

## Before proposing a change

1. Read [SUPPORT.md](SUPPORT.md), the
   [supported-patterns matrix](docs/supported-patterns.md), and the
   [proof-boundary charter](docs/product-charter.md). Analyzer changes must also
   follow the [contributor fixture contract](docs/contributor-fixtures.md).
2. Use the matching issue form. Security vulnerabilities must follow
   [SECURITY.md](SECURITY.md), never a public issue.
3. Remove client names, credentials, private paths, business identifiers, source
   snippets, and generated architecture artifacts. Prefer a minimal synthetic
   repository or `.ts.txt` fixture.
4. For a new framework pattern, link its public documentation and state which package
   and symbol identity the analyzer can prove.

## Development setup

Use Node.js and pnpm versions admitted by `package.json`; a manifest range is not a
claim that every combination has passed the maintained compatibility matrix.

```powershell
pnpm install --frozen-lockfile --ignore-scripts
pnpm run build
pnpm run typecheck
pnpm run lint
pnpm run test
pnpm run format:check
```

Some integration tests need package assets already present in the lockfile install.
Tests must not start or import target applications, contact their databases or
brokers, or depend on private sibling repositories.

## Evidence contract for analyzer changes

An extractor or tracing change normally needs all of the following:

- one positive synthetic fixture proving the supported pattern;
- one close negative preventing same-name or shape-only inference;
- an ambiguity, dynamic, unsupported, or limit case where proof can stop;
- exact diagnostic, assertion, evidence, and canonical-order expectations;
- a `mustNotInfer` assertion for the most dangerous overclaim; and
- documentation updates in `docs/supported-patterns.md` and the detailed feature guide.

The fixture contract separates positive, close-negative, diagnostic, evidence,
compatibility, and performance evidence. Real-package compatibility and performance
observations are independent from declaration-stub semantic fixtures; do not use one
to imply the other.

Schema changes additionally require a version decision, strict validator updates,
canonical ordering, compatibility-reader coverage, and migration/release notes.
Generated bundles and schemas must be regenerated by their owning build command and
reviewed as derived artifacts.

## Pull requests

Keep changes bounded and explain the user problem before the implementation. The pull-
request template asks for the changed proof boundary, verification evidence, fixture
provenance, and artifact-safety review. A passing test is not permission to broaden a
public claim beyond its exact fixture and environment.

Maintainers may decline speculative framework breadth, name-based heuristics, runtime
execution of target code, unbounded output, or changes that erase uncertainty. See
[GOVERNANCE.md](GOVERNANCE.md) for decision authority.

## Contribution licensing and DCO

The project uses **inbound equals outbound**: contributions are submitted under the
repository's Apache License 2.0. No CLA is currently required. Every commit must also
certify the [Developer Certificate of Origin 1.1](https://developercertificate.org/)
with a sign-off matching the commit author's name and email:

```text
Signed-off-by: Contributor Name <contributor@example.com>
```

Use `git commit -s`. Every `Co-authored-by` identity must have a matching
`Signed-off-by` trailer. Fix missing sign-offs by amending or rebasing your own commits;
do not add another person's certification without their authorization.

The repository-local check can be run as:

```powershell
node scripts/check-dco.mjs --range <base-commit>..<head-commit>
```

The public repository must require the `DCO / signed-off commits` check before pull
requests can merge. Changes to `.github/**`, `scripts/check-dco.mjs`, governance, or
release policy require owner review under `CODEOWNERS`; a passing PR-controlled check
alone is not approval. DCO records are public contribution metadata and may be retained
indefinitely with the Git history.

## Provenance and privacy

Contributors must have the right to submit every source, fixture, screenshot, schema,
and generated asset. Do not copy client code into a “synthetic” fixture by renaming
identifiers. Permission to run this analyzer against an organization's systems is not
permission to contribute material derived from those systems. Record every new fixture
or media asset in `docs/legal/fixture-provenance.md` and update redistribution evidence
when adding or bundling a dependency or asset.

Before attaching support material, follow the
[source-free diagnostic manifest guide](docs/support-diagnostic-manifest.md). Redaction
reduces risk but is not a confidentiality guarantee.
