# 0.1.0-alpha.1 Release Candidate

Status: audited O5.2 publication candidate. The sanitized source repository and private
reporting channels are active; this record does not itself create a tag, package, OCI
image, GitLab component, or public issue channel.

## Positioning

api-intel provides evidence-backed blast radius for legacy NestJS systems. It proves
supported static paths to potential side-effect operations and reports exactly where
proof stops. It does not execute a target application or claim complete runtime
reachability.

## Version domains

- npm/CLI package: `0.1.0-alpha.1`;
- analysis document: v8;
- project configuration: v4;
- MCP server: v1.2.0; and
- every comparison, impact, policy, graph, CI, and system document retains its own
  independent schema version.

The prerelease does not change those independent schema versions merely to match the
package version.

## Migration notes

This is the first selected public prerelease candidate, so there is no supported
published version to upgrade from. Existing private-development users should:

1. run `api-intel doctor <repository>` and resolve only actionable readiness gaps;
2. keep version-4 configuration and explicitly configured critical-section wrappers;
3. regenerate analysis rather than editing a prior artifact or treating an old graph
   as current evidence; and
4. compare schema versions independently instead of assuming package-version lockstep.

Alpha CLI, configuration, report, and schema contracts may change. A later change to a
supported reader or workflow must include explicit migration guidance.

## Installation and immutable references

O5.1 validates only the content-addressed local tarball in the retained candidate
directory. It does not document a registry install before publication. GitHub Action
consumers must replace `ACTION_COMMIT_SHA` with a full commit SHA. GitLab consumers
must pin the component by full commit SHA and the OCI image by registry manifest
digest (`@sha256:...`); version tags are not supported consumption references.

## Rollback and compromise

There are no external O5.1 bytes to roll back. After publication, released bytes and
tags must never be replaced. Fix forward with a new prerelease, or follow the bounded
deprecation/unpublishing and compromised-release procedure in
[Release Integrity and Response](../release-integrity-and-response.md).

## Remaining release boundaries

- the exact release commit must pass the clean hosted matrix before tag/package
  publication;
- exact OCI base/image SBOM, manifest digest, and corresponding-source obligations
  require release-specific review;
- GitLab-hosted component execution remains deferred; and
- no named browser matrix is claimed.

The independent boundaries are retained in the machine-readable candidate manifest and
cannot be converted into passing claims by this document.
